## 阶段性发现（需后续验证确认）

### 发现 1：1.5B 模型在 AI 搜索的生成任务上不可用

Qwen2.5-1.5B 的平均分 22.5，94% 的答案被判定为不可用（D/F 级）。核心失败模式不是「知识不足」，而是**没有执行 AI 搜索的行为范式**：
- 引文质量：86% 的答案零引用（完全无视 prompt 中「标注来源」的要求）
- 整合质量：64% 的答案简单罗列，未做任何多文档融合
- 准确性：24% 的答案存在严重事实错误

> ⚠️ 注：50 条样本。1.5B 的 context window 达 32K，理论上能容纳全部输入。失败原因可能是 attention 在长上下文（~6000 tokens）中退化，或 prompt 遵循能力不足。需补满 200 条确认。

### 发现 2：Qwen3 的思考模式在 AI 搜索场景下轻微有害

Qwen3-4B non-thinking 在 6 个维度上全面不低于 thinking 模式（50 条对照 + 198 条单边验证）。

**50 条对等对照**（thinking 仅 Judge 了 50 条）：

| 维度 | non-think (50) | thinking (50) | Δ |
|------|:-------------:|:-----------:|:---:|
| 准确性 | 3.08 | 2.90 | +0.18 |
| 相关性 | 3.66 | 3.48 | +0.18 |
| 用户体验 | 3.16 | 3.10 | +0.06 |
| 整合质量 | 2.26 | 2.28 | -0.02 |
| 引文质量 | 2.42 | 2.42 | 0.00 |
| **总分** | **59.0** | **57.4** | **+1.6** |

non-thinking 在 4 个关键生成维度上优于 thinking，仅整合质量微输。扩大到 198 条后 non-thinking 总分 60.2（甚至比 50 条更高），说明小样本未高估。

> ⚠️ 注：thinking 模式仅 50 条样本，差距未达显著。需补满 200 条后做配对 t 检验确认。

**与官方结论的一致性分析**：

「Qwen3 思考模式普遍提升 benchmark 分数」的官方结论来自以下几类 benchmark：

| Benchmark 类型 | 思考模式效果 | 代表测试 | 任务特征 |
|---------------|:----------:|---------|---------|
| 数学推理 | ✅ 大幅提升 | AIME 2024: 73.8% (超过 R1-Distill-32B 的 72.6%) | 需要内部链式推理 |
| 知识问答 | ✅ 中幅提升 | MMLU-Redux: 83% → 86% | 依赖参数化知识 |
| 代码生成 | ✅ 中幅提升 | LiveCodeBench v5: 48.4 → 65.6 | 需要逐步规划 |
| 长上下文检索 | ❌ 下降 | RULER: thinking 模式有害 | 需要从外部文档提取信息 |
| **AI 搜索生成** | **❌ 下降** | **本实验: 60.2 → 57.4 (-2.8)** | **需要忠实复现外部文档** |

> **来源支撑**：
> 1. Qwen3 官方技术报告明确标注：「Thinking mode hurts retrieval-heavy tasks (e.g., RULER)」—— [Qwen3 Technical Report](https://arxiv.org/abs/2505.09388)
> 2. 阿里云百炼平台官方实践建议：非思考模式适用于「知识库检索、客服问答」场景，响应速度提升 60%，算力仅为思考模式的 1/3 —— [CSDN 阿里云官方技术文章](https://blog.csdn.net/weixin_72532546/article/details/160226282)
> 3. Qwen3 官方博客：思考模式适合「需要深度思考的复杂问题」，非思考模式适合「速度比深度更重要的简单问题」—— [Qwen3 官方博客](https://qwenlm.github.io/blog/qwen3/)
> 4. 第三方评测：Qwen3-4B thinking 在 AIME 2024 得分 73.8%，超过 R1-Distill-32B (72.6%)，但在检索依赖型任务上表现显著下降 —— [InsiderLLM](https://insiderllm.com/pdfs/best-local-llms-math-reasoning.pdf)
> 5. 论文 "Thinking Small Models are Efficient LLM Judges" 证明 thinking 在 LLM-as-a-Judge 任务上 +10pp 准确率，但该任务需要内部按 Rubric 推理，与 AI 搜索的「忠实于外部文档」需求相反 —— [arXiv:2509.13332](https://arxiv.org/abs/2509.13332)

**结论**：本实验发现并非反常，而是精确命中了 Qwen3 官方标注的局限范围。思考模式的收益高度依赖于任务是否以「内部推理」为核心——数学/代码/逻辑推理受益，知识库问答/AI 搜索/文档检索受损。在 AI 搜索的生成环节，**应默认禁用思考模式**。

```
                        思考模式有益 ←────────→ 思考模式有害
                              │                      │
          数学推理 AIME MATH-500  │    知识库问答 RULER
          代码生成 LiveCodeBench  │    AI 搜索生成 （本实验）
          Judge 评分 RewardBench  │    阿里云百炼 官方建议
                              │                      │
              任务需要          │         任务需要
           "内部链式推理"        │      "忠实于外部文档"
```

> ⚠️ 注：thinking 模式仅 50 条样本，需补满 200 条后做配对 t 检验。

### 发现 3：「整合」仍是天花板——连 qwen3-max 也未突破

- **整合质量**：所有模型仍无人得 4 分。qwen3-max 的最高分停在 3（64% 达 3 分），Qwen3-4B-nt 46% 达 3 分，Qwen2.5-7B 仅 23% 达 3 分。**多文档深度融合不是模型大小问题——即使是强大如 qwen3-max 的 API 模型，也无法在 1024 token 预算内做到「深度整合 + 跨文档推理 + 矛盾处理」三合一的 4 分水平。**这可能是当前评测框架（单轮生成 + token 预算限制）本身的难度上限。
- **引文质量**：qwen3-max 有 76% 的答案引文达 3 分（vs 4B-nt 57% / 7B 23%），且仅 2% 的答案引文为 1 分（vs 7B 15%）。但关键的区别不在于「零引用」——qwen3-max 和 7B 的 1 分率相近（2% vs 15%），而在于**7B 的引文停留在「有但粗糙」的 2 分区（63%），qwen3-max 则进入「可靠」的 3 分区（76%）**。

### 发现 4：Qwen3-4B 全面超越 Qwen2.5-7B —— 「小模型大能力」宣告成立

198 条对等比较下，Qwen3-4B-nonthink 在 5/6 维度上超越 7B（safety 打平），总分高 4.2 分，Pass% 高 19 个百分点。

**7B 的核心短板**：

| 问题 | 数据 |
|------|------|
| 引文太粗糙 | 63% 只拿 2 分（vs 4B 的 30%） |
| D 级占比爆炸 | 58.6%（116 条）被判定「不可用」 |
| A+B 级占比低 | 仅 20%（40 条），vs 4B 的 47%（94 条） |
| 整合能力弱 | 72% 停在 2 分，仅完成「基本归类」，缺乏深度 |

**工程含义**：
- Qwen3-4B 以 57% 的参数量（4B vs 7B）和约 50% 的 VRAM（8GB vs 14GB），在 AI 搜索任务上实现了 **+4.2 分 (+7.5%)** 的显著优势
- 之前担心 Qwen3-4B 的 50 条分数被噪声撑高，198 条反而更高（59.0 → 60.2），说明数据稳
- Qwen 官方「Qwen3-4B 媲美 Qwen2.5-72B」的 meta-claim 在 AI 搜索场景下部分成立：至少「Qwen3-4B 超越 Qwen2.5-7B」已确证

> ⚠️ 注：需与 DeepSeek-chat 上界相比后，才能判断本地模型距离「可用」还差多远（当前 60.2 分虽为最高但仍处于及格线上方）。

### 发现 5：qwen3-max 确立了 API 模型的「高 12.5 分」优势线

qwen3-max 作为第一个参评的强 API 模型，总分为 72.7，超过最佳本地模型 Qwen3-4B-nt（60.2）整整 12.5 分。这个差距分布在每一个维度上，且每一维都够大：

| 维度 | q3-max | 最佳本地 | 差距 | 含义 |
|------|:------:|:------:|:---:|------|
| 用户体验 | 3.58 | 3.11 (4B-nt) | **+0.47** | 最大差距：API 模型在回答结构和表达上远超开源 |
| 引文质量 | 2.75 | 2.45 (4B-nt) | +0.30 | API 模型的引用更精准、更可靠 |
| 准确性 | 3.43 | 3.10 (4B-nt) | +0.33 | API 模型更少出现事实偏差 |
| 整合质量 | 2.62 | 2.31 (4B-nt) | +0.31 | 所有维度中最难的，差距却偏小——说明这不是「强模型能轻松碾压」的维度 |
| 相关性 | 3.91 | 3.68 (4B-nt) | +0.23 | 相关性差距最小，因为相关性惩罚本身就少 |
| 安全性 | 3.80 | 3.64 (4B-nt) | +0.16 | 所有模型安全分数都高，区分度低 |

**关键信号**：
- **用户体验是 API 模型对本地模型的最大优势维度**（+0.47）。这不是「知识差距」，而是 qwen3-max 在回答的格式、结构、措辞、可读性上的系统性碾压——这些是预训练+后训练（RLHF/DPO）中大量对齐数据才能塑造的能力。
- **整合质量差距最小**（+0.31），且 qwen3-max 也未能突破 4 分天花板。这再次确认：多文档深度融合不是当前 LLM 的强项，无论多大、多强。
- **81.2% Pass%、137 条 A+B 级**：qwen3-max 的等级分布接近正态（A 70 + B 67 + C 23 + D 36 + F 1），没有 7B 那种 D 级系统性爆炸的问题。D 级仅 18.3%（vs 7B 的 58.6%）。

**工程含义**：
- 如果目标是「60 分及格可用」，本地 Qwen3-4B 已经越过这条线
- 如果目标是「70 分好用」，当前唯一的路是调 API（qwen3-max 或 DeepSeek-chat）
- 本地模型与 API 模型的核心差距不在「知不知道答案」（准确性 +0.33），而在「答得怎么样」（用户体验 +0.47、引文 +0.30）

### 发现 6：双 Judge (thinking) 校准 — ±1 一致率 92%+，Judge 体系可靠性初步验证

> 版本：2026-05-31。基于 Qwen3-4B-nothink 生成的 198 条答案，从已有 answers 文件中简单随机采样 150 条（calibration 50 + verification 100），双 Judge 共评 146 条（4 条因 API 错误丢弃）。Judges **均开启 thinking 模式**。

#### Judge 配置

| 项目 | Judge A | Judge B |
|------|---------|---------|
| 模型 | deepseek-reasoner | glm-4.7 |
| 提供商 | DeepSeek API | 智谱 API (open.bigmodel.cn) |
| 思考模式 | ✅ thinking (native) | ✅ thinking (`thinking: {type: enabled}`) |
| Max tokens | 4096 | 4096 |
| Temperature | 1.0 (reasoner 要求) | 1.0 (GLM-4.7 默认) |

#### 一致性矩阵（146 条）

| 维度 | Exact | ±1 | Kappa | Spearman ρ | Δ(A−B) | A mean | B mean |
|------|:-----:|:---:|:-----:|:----------:|:------:|:------:|:------:|
| 准确性 | 0.616 | **0.918** | 0.391 | 0.618 | −0.212 | 3.12 | 3.34 |
| 安全性 | 0.596 | **1.000** | 0.165 | 0.204 | +0.075 | 3.64 | 3.57 |
| 相关性 | **0.760** | 0.966 | 0.449 | **0.705** | −0.014 | 3.55 | 3.56 |
| 整合质量 | 0.719 | **0.980** | **0.531** | 0.701 | −0.151 | 2.31 | 2.46 |
| 引文质量 | 0.651 | **0.980** | 0.475 | **0.745** | −0.151 | 2.31 | 2.46 |
| 用户体验 | 0.589 | **0.986** | 0.358 | 0.542 | 0.000 | 3.08 | 3.08 |

> ⚠️ Spearman ρ 使用了 scipy.stats.spearmanr（正确处理 tie）。手写 fallback 公式 `1−6Σd²/(n(n²−1))` 在 1-4 分量表存在大量 tie 时会虚假放大 ρ（之前 β 报告 ρ=1.000 即为此 bug），已修复。

#### 关键发现

**1. 两位 Judge 没有严重分歧。** ±1 一致率全部 ≥ 0.918，引文和整合质量更是达 0.980。所有 146 个样本中，不存在差 2 档以上的评分冲突。

**2. DeepSeek 整体偏严**，但幅度可控。五个维度 Δ(A−B) 为负（deepseek-reasoner 给分更低），平均偏严 −0.106 档。最明显的是准确性 (−0.212) 和整合/引文 (−0.151)。偏严意味着 deepseek 在 judge 任务上更难被「忽悠」——这对 AI 搜索评估是优点而非缺陷。

**3. 引文和整合质量是分歧最小的维度。** 这两个维度是生成任务的技术瓶颈，评分标准相对客观（「有没有引文」「是否做了多文档融合」），Judge 最容易对齐。相反，安全性和用户体验更依赖主观判断（「排版是否不错」「有没有潜在风险暗示」），一致率相对偏低。

**4. 安全性维度缺乏区分度。** 两个 Judge 在安全性上的平均分均为 3.6+（接近满分），分布集中在 3-4 档。Kappa=0.165、ρ=0.204 不是「Judge 不一致」，而是「几乎没有低分样本」——大多数答案本身就很安全，Judge 没有理由打低分。如需更细粒度的安全性评估，可引入针对性的对抗样本。

**5. Kappa 偏低是小范围量表 + 分数集中的正常现象。** Kappa 扣除了随机一致的部分（$P_e$），当评分集中在 3-4 档时 $P_e$ 很高，导致 Kappa 被压缩。±1 一致率（0.92-1.00）比 Kappa 更能反映可用性。

#### 技术实现笔记

- **LangChain ChatOpenAI 丢弃 `reasoning_content`**：LangChain 1.x 的 `AIMessage` 不映射厂商扩展字段（DeepSeek 的 `reasoning_content`、GLM 的同名字段）。解决方案：在 `generate_with_reasoning()` 中改用原生 `openai.OpenAI` 客户端直调 API，`chat.completions.create` 返回的 `choice.message.reasoning_content` 可直接获取完整思考链。
- **智谱 API base URL**：文档标注为 `https://open.bigmodel.cn/api/paas/v4/`（非 `api.z.ai`）。
- **`extra_body` 替代 `model_kwargs`**：langchain-openai 1.2.x 移除了 `model_kwargs` 参数，改为 `extra_body` 透传。
- **并发 + 错峰**：Judge A 和 B 各用 `ThreadPoolExecutor(max_workers=2+3.0s stagger)` 并行，5 条测试 0 失败 0 限流。GLM thinking 模式下 API 延迟较高（~50-90s/次），建议 concurrency≤2。

> ⚠️ 注：当前 Judge 评分（deepseek-chat 对模型的 198 条评分）尚未使用双 Judge 体系。将全部模型评估迁移到双 Judge 体系的工作正在进行中。

## 关键技术决策记录

以下决策在实验设计和实现中做出，记录供后续备忘：

| 决策 | 选择 | 理由 |
|------|------|------|
| Judge 评估策略 | 两批 × 3 维（非一次 11 维、非一次 1 维） | 一次 11 维认知过载（后面维度被敷衍），一次 1 维缺少跨维度关联且调用量过大。每批 3 维平衡注意力和调用成本 |
| 生成 prompt | 单套通用（非 5 套分类型） | 分类器不准 + 分类型 prompt 引入混淆变量，同一套 prompt 确保模型对比是 apples-to-apples |
| 查询采样 | 简单随机 200 条（非分层） | 关键词分类器准确率仅 ~70%，分层引入噪声。保留分类标签仅用于后验分析 |
| 查询来源 | 从 reranker cache 提取（非 queries.dev.tsv） | ID 空间不匹配——dev.tsv 有 24831 条但 reranker 仅覆盖 1824 条 |
| 评估维度 | 先 6 维核心，后续扩展至 11 维 | 控制初版复杂度。5 个扩展维度（指令遵循、上下文利用、拒答判断、结构适配、内部一致性）的 prompt 已预置在代码中 |
